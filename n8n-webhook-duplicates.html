N8N WEBHOOK RELIABILITY

Retries are normal. Duplicate business actions are optional.

Webhook senders may retry after timeouts, connection loss, or ambiguous responses. An idempotent workflow recognizes the same event and prevents a second invoice, lead, ticket, or notification.

Start with a stable event key

Prefer an event ID supplied by the sender. If none exists, derive a key only from fields that identify the same business event across retries. A timestamp generated when the request arrives is not stable and will make every retry look new.

Claim the event before the irreversible action

1. ReceiveValidate authentication, structure, and required fields.
2. ClaimAtomically store the event key or detect that it already exists.
3. ExecutePerform the external write once and store the resulting record ID.

The claim must happen before the side effect. A simple “search, then insert” sequence can still race when two deliveries arrive together; use a unique constraint, atomic insert, or equivalent single-winner operation in the chosen data store.

Define what a duplicate should return

A duplicate is often not an error. Return a successful response when the earlier event completed, and an appropriate in-progress response when processing is still active. Preserve the original result identifier when the caller needs it. The exact response depends on the sender’s documented retry behavior.

Handle the ambiguous middle state

The hardest case is a timeout after the external service may have accepted the write. Use a provider-supported idempotency key when available. Otherwise query by a stable external reference before attempting the write again. Do not assume that a timeout means “nothing happened.”

Choose retention deliberately

Keep idempotency records for at least as long as the sender may retry, plus any manual replay window. Permanent financial or compliance events may require longer retention than ordinary notifications. Document cleanup so storage does not grow without limit.

Test more than sequential duplicates

  • Send the same event twice, one after the other.
  • Send two copies concurrently.
  • Force a timeout after the external write.
  • Replay after the workflow version changes.
  • Confirm that two genuinely different events are not collapsed.

The final assertion belongs in the downstream system: exactly one intended business record should exist.

Keep test and production inputs separate

Use distinct webhook URLs and fixtures for test and production. Reject malformed requests early, keep examples sanitized, and document which environment produced each validation result.
