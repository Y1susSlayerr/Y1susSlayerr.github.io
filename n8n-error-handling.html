N8N PRODUCTION GUIDE

Error handling that fails loudly—and recovers safely.

A successful execution badge is not the same as a successful business outcome. Use this checklist to make errors observable, retries bounded, and recovery predictable.

1. Classify the failure before retrying

Temporary failures such as rate limits, gateway errors, and short network interruptions may justify a retry. Invalid credentials, malformed payloads, permission errors, and rejected business rules usually do not. Retrying permanent failures adds noise and may intensify an outage.

2. Put a hard bound on retries

Every retry policy needs a maximum attempt count and a delay. For rate-limited services, respect the provider’s retry guidance when available. Record the attempt number so alerts and later analysis can distinguish the first failure from the terminal one.

3. Separate terminal errors from optional branches

“Continue on fail” can be appropriate for an optional enrichment step, but dangerous on the node that creates an invoice, updates inventory, or sends a customer notification. Document which failures may continue and route every terminal error to an explicit recovery path.

4. Alert with useful context—without secrets

An alert should identify the workflow, execution, failing node, timestamp, sanitized record identifier, and next action. Do not include credentials, authorization headers, full customer records, or raw webhook bodies. Link operators to the internal execution record when access is controlled.

5. Plan for partial writes

A workflow can fail after one external system has already accepted a change. Decide whether recovery should roll the change back, continue from the last confirmed step, or safely replay the complete event. Track the external record IDs needed to make that decision.

6. Test the failure path deliberately

  • Invalid or missing required input.
  • A temporary upstream failure followed by recovery.
  • A permanent rejection that must not retry.
  • A timeout or ambiguous external response.
  • A failure inside the alerting path itself.

Verify downstream records, not only n8n’s execution status. Confirm whether each intended write happened zero times, once, or more than once.

7. Keep rollback and replay separate

A rollback restores a known safe workflow version. A replay reprocesses business events. Store dated exports, define the rollback trigger, identify the responsible operator, and document which events are safe to replay. Never assume that replaying a failed execution is harmless.
